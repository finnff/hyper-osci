## 2. Technical Analysis

### 2.1 Audio Bandwidth Requirements

Oscilloscope rendering requires continuous stereo audio:

| Parameter | Value |
|-----------|-------|
| Sample Rate | 44,100 - 192,000 Hz |
| Bit Depth | 12-16 bit |
| Channels | 2 (X=Left, Y=Right) |
| **Uncompressed bitrate** | **1.4 - 6.1 Mbps per scope** |
| **4 scopes total** | **5.6 - 24.4 Mbps** |

**Conclusion:** Raw audio streaming is bandwidth-intensive but feasible over WiFi 5/6.

### 2.2 Latency Budget (Live Performance)

| Stage | Target Latency |
|-------|----------------|
| Audio generation (PC) | < 5ms |
| Network transmission | < 10ms |
| Buffer/jitter compensation | 10-20ms |
| DAC output | < 1ms |
| **Total end-to-end** | **< 40ms** |

**Acceptable for visual sync** (human perception ~100ms for audio-visual desync).

### 2.3 Synchronization Challenges

**Problem:** 4 independent devices must output identical waveforms at the exact same time.

**Challenges:**
1. **Clock drift** - Each MCU has slightly different clock frequency
2. **Network jitter** - WiFi packets arrive at varying times
3. **Buffer underrun/overrun** - If playback catches up to or falls behind data
4. **Phase alignment** - All 4 outputs must be in phase

**Solutions (ranked by complexity):**

| Approach | Complexity | Sync Accuracy |
|----------|------------|---------------|
| NTP-based soft sync | Low | ±10ms |
| PTP (Precision Time Protocol) | Medium | ±100μs |
| Hardware sync line (GPIO trigger) | Medium | ±1μs |
| GPS PPS (Pulse Per Second) | High | ±50ns |
| Shared master clock (daisy chain) | High | Sample-accurate |

## 3. Architecture Options

### 3.1 Option A: Audio Streaming (Recommended for v1)

**Concept:** PC generates audio, streams raw samples to slaves via WiFi.

```
PC (osci-render) ──UDP multicast──▶ ESP32 ──I2S──▶ DAC MCU ──analog──▶ Scope
```

**Pros:**
- All rendering on powerful PC
- Slaves are "dumb" audio players
- Easy to update visuals (just change PC software)

**Cons:**
- High bandwidth (~6 Mbps per slave at 48kHz/16bit)
- Requires jitter buffer
- WiFi reliability concerns for live performance

**Implementation:**
```
┌─────────────┐      ┌─────────────┐      ┌─────────────┐
│     PC      │      │   ESP32     │      │  DAC MCU    │
│             │      │             │      │ (RA4M1/STM) │
│ osci-render │─UDP─▶│ WiFi RX     │─I2S─▶│             │
│ (4 streams) │      │ Buffer      │      │ 12-bit DAC  │──▶ Scope
│             │      │ Sync logic  │      │ X + Y out   │
└─────────────┘      └─────────────┘      └─────────────┘
```

### 3.2 Option B: Command Streaming

**Concept:** PC sends high-level commands (shapes, parameters), slaves render locally.

```
PC (controller) ──commands──▶ ESP32 ──▶ Local renderer ──▶ DAC ──▶ Scope
```

**Pros:**
- Very low bandwidth (< 100 kbps)
- Works over poor WiFi
- Can run independently if connection drops

**Cons:**
- Need to port osci-render engine to MCU (very complex)
- Limited MCU processing power (no complex effects)
- Harder to sync (each device renders independently)

**Feasibility:** LOW for full osci-render features, but possible for simple shapes.

### 3.3 Option C: Hybrid Buffered Playback

**Concept:** Pre-render sequences on PC, distribute as files, play synchronized.

```
PC (pre-render) ──WiFi──▶ ESP32 (store to flash) ──▶ Sync playback ──▶ Scope
```

**Pros:**
- No real-time streaming needed
- Can work offline after sync
- Easy to ensure identical output

**Cons:**
- Not truly real-time (visuals must be pre-planned)
- Large flash storage needed
- Less flexible for live improvisation

### 3.4 Option D: Multi-Output Audio Interface (Simplest)

**Concept:** Use a single PC with a multi-channel audio interface.

```
PC ──▶ 8-channel audio interface ──▶ 4× stereo outputs ──▶ 4× Scopes
```

**Hardware examples:**
- Focusrite Scarlett 18i20 (8 outputs)
- MOTU 8A (8 outputs)
- RME Fireface UCX II (8 outputs)

**Pros:**
- Simplest implementation
- Perfect sync (same audio interface)
- No custom hardware needed

**Cons:**
- Needs wired connections to all scopes
- Less "cool" than distributed system
- Single point of failure

#### 4.2.2 ESP32 Firmware (C/C++ with ESP-IDF or Arduino)

```cpp
// Pseudocode structure
class HyperOsciSlave {
    // Network
    WiFiUDP udp;
    CircularBuffer<int16_t> audioBuffer;  // Jitter buffer (50-100ms)
    
    // Sync
    uint64_t masterTime;      // NTP-synced time
    uint32_t playbackOffset;  // Compensate for network latency
    
    // I2S output to DAC MCU
    I2SStream i2sOut;
    
    void setup() {
        connectWiFi();
        syncTime();           // NTP sync
        discoverMaster();     // mDNS discovery
        startI2S();
    }
    
    void loop() {
        // Receive audio packets
        if (udp.parsePacket()) {
            AudioPacket pkt = parsePacket(udp);
            audioBuffer.write(pkt.samples, pkt.timestamp);
        }
        
        // Output samples at correct time
        while (audioBuffer.available() && shouldPlayNow()) {
            Sample s = audioBuffer.read();
            i2sOut.write(s);
        }
    }
};
```

### 4.3 Network Protocol Design

#### 4.3.1 Packet Format

```
┌─────────────────────────────────────────────────────────────────────┐
│                        AUDIO PACKET (UDP)                           │
├─────────────────────────────────────────────────────────────────────┤
│ Offset │ Size │ Field           │ Description                       │
├────────┼──────┼─────────────────┼───────────────────────────────────┤
│ 0      │ 4    │ Magic           │ 0x4F534349 ("OSCI")               │
│ 4      │ 4    │ Sequence        │ Packet sequence number            │
│ 8      │ 8    │ Timestamp       │ Playback time (microseconds)      │
│ 16     │ 2    │ Sample Rate     │ 44100 / 48000 / 96000             │
│ 18     │ 2    │ Sample Count    │ Number of stereo samples          │
│ 20     │ N    │ Audio Data      │ Interleaved L/R int16 samples     │
└─────────────────────────────────────────────────────────────────────┘
```

**Example:** 10ms of 48kHz audio = 480 samples × 2 channels × 2 bytes = 1920 bytes + 20 byte header = 1940 bytes per packet.

#### 4.3.2 Sync Protocol

```
1. DISCOVERY (mDNS)
   - Master announces: _hyperosci._udp.local
   - Slaves discover and register

2. TIME SYNC (NTP-like)
   - Master sends SYNC packets every 1 second
   - Slaves calculate round-trip time and offset
   - Target accuracy: < 1ms

3. PLAYBACK SYNC
   - Each audio packet has absolute timestamp
   - Slaves buffer ~50ms ahead of playback
   - Playback starts when local_time >= packet_timestamp

4. HEARTBEAT
   - Slaves send status every 100ms
   - Master monitors buffer levels, adjusts timing
```

### 4.4 Synchronization Strategy

#### 4.4.1 Software Sync (NTP-based)

**Accuracy:** ±1-10ms (usually sufficient for visual sync)

```python
# Master side
def send_audio_packet(samples):
    timestamp = current_time_us() + BUFFER_AHEAD_US  # e.g., +50ms
    packet = AudioPacket(
        sequence=next_seq(),
        timestamp=timestamp,
        samples=samples
    )
    multicast_socket.send(packet)

# Slave side
def play_audio():
    while True:
        if buffer.peek().timestamp <= current_time_us():
            sample = buffer.pop()
            i2s.write(sample)
```

#### 4.4.2 Hardware Sync (GPIO Trigger)

For tighter sync, add a physical sync line:

```
Master GPIO ────┬────▶ Slave 1 GPIO (interrupt)
                ├────▶ Slave 2 GPIO
                ├────▶ Slave 3 GPIO
                └────▶ Slave 4 GPIO
```

The master sends a pulse at the start of each "frame" (e.g., every 100ms). Slaves reset their playback position on this trigger.

**Wiring:** Single wire from PC (via USB-GPIO adapter like FTDI) to all slaves (active-low, 3.3V logic).

### 4.5 Microphone Integration

#### 4.5.1 Option: Mix on PC

```
Microphones ──▶ Audio Interface ──▶ PC ──▶ Mix with osci-render ──▶ Distribute
```

**Best for:** Full control over mixing, effects, synchronization.

#### 4.5.2 Option: Local Mic Input on Slaves

```
Each Slave: Local MAX4466 ──▶ ESP32 ADC ──▶ Mix with network audio ──▶ DAC
```

**Best for:** Independent audio visualization per scope, reduced network load.

#### 4.5.3 Recommended: Hybrid

- **osci-render visuals:** Generated on PC, distributed to all slaves (identical)
- **Microphone input:** Local on each slave (can be different per scope, or same if using single mic → PC → distribute)

## 6. Alternative: Run osci-render on Embedded Device?

### 6.1 Feasibility Analysis

**Question:** Can we run osci-render (or similar) directly on ESP32/STM32?

**Requirements for osci-render:**
- C++ with JUCE framework (requires desktop OS)
- ~100MB RAM typical usage
- Floating-point math for effects
- File I/O for loading assets

**ESP32 Specs:**
- 520KB SRAM
- 240MHz dual-core
- No FPU (software float, slow)
- No JUCE support

**Conclusion:** ❌ Full osci-render cannot run on ESP32/STM32.

### 6.2 What CAN Run on Embedded?

**Simple shape generators:**
```cpp
// ESP32 can generate basic Lissajous figures
void generate_circle(float* x_buf, float* y_buf, int samples, float freq) {
    for (int i = 0; i < samples; i++) {
        float t = (float)i / SAMPLE_RATE * freq * 2 * M_PI;
        x_buf[i] = cosf(t);
        y_buf[i] = sinf(t);
    }
}
```

**What's possible on MCU:**
- Basic shapes (circle, square, triangle, line)
- Simple Lissajous patterns
- Audio visualization (FFT spectrum)
- Pre-loaded lookup tables

**What's NOT possible:**
- SVG/OBJ rendering
- Complex effects (wobble, kaleidoscope)
- Text rendering
- Lua scripting

### 6.3 Hybrid Approach

Run simple visualizations locally on slaves, but receive complex visuals from PC:

```
PC: Complex osci-render ──network──▶ Slave buffer
                                         │
Slave: Simple local patterns ────────────┤
                                         ▼
                                    DAC output
```

The slave can crossfade between network audio (when available) and local patterns (when network drops).
